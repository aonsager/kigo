# Kigo — agent guide

Domain vocabulary lives in [CONTEXT.md](./CONTEXT.md); the goal state and its
evidence procedures live in [docs/GOAL.md](./docs/GOAL.md). This file is the
operational guide for any agent (especially the afk-loop implementer) touching
the code: how to build, how to test, and the traps that waste whole iterations.

## Stack

SwiftUI app + WidgetKit extension + StoreKit 2. Swift 6 / **Xcode 26.5** (see the
toolchain note under Build & test — the simulator *runtime* pin is still 26.4.1).
The Xcode project is generated by **XcodeGen** from `project.yml` and is
**gitignored** — never edit `Kigo.xcodeproj` by hand; edit `project.yml` and
regenerate.

## Build & test — two lanes

Domain logic lives in the local SPM package **`KigoCore/`** and is tested
host-side with no simulator anywhere in the stack (see
`docs/kigocore-migration-plan.md`). **Run the fast lane first, always** — it is
two orders of magnitude faster and immune to every simulator failure mode in
this file:

```bash
# FAST LANE — KigoCore domain logic (~60+ tests in <1s, no simulator):
scripts/xctimeout 300 swift test --package-path KigoCore
```

Success signal: exit 0 (`swift test` prints standard `Executed N tests`
summaries). Anything that changes KigoCore sources/tests gates on this lane.
The sim lane below is required only for changes touching the app/widget
targets, UI behavior, or screenshot evidence.

When adding logic, put it (and its tests) in KigoCore unless it genuinely needs
SwiftUI/UIKit/WidgetKit/StoreKit — the package is deliberately free of those so
its tests can never hit a simulator wedge. StoreKit conformances live app-side
(`StoreKitEntitlement.swift`); shared test fakes live in the
`KigoCoreTestSupport` product (importable from both lanes).

### Sim lane

Always regenerate the project first, then run the hardened test command. Do
**not** run a bare `xcodebuild test` — the extra flags below are load-bearing
(see "Why the flags" — they are what turns a hung test into a fast failure).

```bash
xcodegen generate
# Pin by UDID, pre-booted. The afk wrapper resolves iPhone 17 / iOS 26.4 and
# boots it each iteration (.afk/sim-udid); the fallback resolver below covers
# standalone sessions. NEVER use `name=…,OS=…` — that destination forces full
# runtime enumeration through a possibly-cold CoreSimulatorService, which is
# exactly where the simdiskimaged wedge fires (SimError 410; see the recovery
# ladder below). Boot-then-`id=` skips that path entirely (verified 2026-07-04).
UDID="$(cat .afk/sim-udid 2>/dev/null)"
[ -n "$UDID" ] || UDID="$(xcrun simctl list devices available -j | python3 -c '
import json, sys
for runtime, devs in json.load(sys.stdin)["devices"].items():
    if "iOS-26-4" in runtime:
        for d in devs:
            if d.get("isAvailable") and d.get("name") == "iPhone 17":
                print(d["udid"]); sys.exit(0)
sys.exit(1)')"
xcrun simctl boot "$UDID" 2>/dev/null || true   # "already booted" is fine
# 12-min inner cap via scripts/xctimeout (a validated perl-alarm wrapper —
# macOS has no coreutils `timeout`) so a hung command fails fast instead of
# wedging the whole afk iteration; XCTest execution-time allowances force a
# single stuck test to fail at 120s. Use xctimeout, NOT a raw perl one-liner —
# see the sandbox trap below.
scripts/xctimeout 720 \
  xcodebuild test \
    -scheme Kigo \
    -destination "platform=iOS Simulator,id=$UDID" \
    -test-timeouts-enabled YES \
    -default-test-execution-time-allowance 120 \
    -maximum-test-execution-time-allowance 300 \
    CODE_SIGNING_ALLOWED=NO \
    -only-testing:KigoTests/<SuiteName>
```

- Pass `** TEST SUCCEEDED **` (exact string) as the success signal. Drop
  `-only-testing:` to run the whole suite.
- **The runtime pin lives in the resolver** (`iOS-26-4` runtime match): still
  the iOS 26.4 runtime, still deliberately off **iOS 26.5** — see the StoreKit
  trap below. The old `name=iPhone 17,OS=26.4.1` destination form is retired:
  it was both nondeterministic across runtimes and the wedge-prone enumeration
  path.

### THE sandbox trap: a raw perl wrapper defeats the xcodebuild sandbox exclusion

Sandbox exclusions in `.claude/settings.json` match on the command string, so
`perl -e 'alarm …' xcodebuild …` runs SANDBOXED (top-level executable is
`perl`; `xcodebuild *` never matches) — and a sandboxed `xcodebuild test`
fails deterministically with the exact wedge signature
(`CoreSimulatorService connection became invalid`, `SimError 409/410`,
`Unable to find a device matching…`) because the sandbox blocks CoreSimulator's
IPC (mach/Unix-socket lookups; cf. claude-code issue #36611). Verified
2026-07-04: identical command, sandboxed → SimError 410 in ~60s; unsandboxed →
`** TEST SUCCEEDED **` in 12s.

**Therefore: wrap timeouts with `scripts/xctimeout`, never a raw perl
one-liner.** It is the same perl-alarm idiom, but name-anchored so the
`scripts/xctimeout *` sandbox exclusion matches reliably, and it refuses to
wrap anything except `xcodebuild`/`xcrun`/`swift`/`xcodegen` — the exclusion
stays exactly as wide as the toolchain that needs it. If `xcodebuild` ever
shows the wedge signature anyway, FIRST rerun with the sandbox explicitly
disabled before reaching for the recovery ladder — sandbox-induced failure is
far more common than a genuine daemon wedge and no amount of service recovery
fixes it.

### Simulator recovery ladder (no sudo, no reboot — verified 2026-07-04)

If an **unsandboxed** `xcodebuild` still fails with the wedge signature while
plain `simctl list` works, the CoreSimulator stack is genuinely wedged (it
happens — documented Apple platform bug, esp. under memory pressure). Recover
with:

```bash
killall -9 com.apple.CoreSimulator.CoreSimulatorService   # user-level; safe between runs
xcrun simctl list devices available >/dev/null             # respawns a fresh service
xcrun simctl boot "$UDID"                                  # warm the pinned device
# then retry the hardened test command (id=$UDID)
```

Two traps:
- **Sandbox:** `killall`/`pkill`/`pgrep` are neutered inside sandboxed Bash
  (`Operation not permitted` from sysctl KERN_PROC). They are listed in the
  sandbox `excludedCommands` in `.claude/settings.json`; if a recovery command
  still hits a sandbox error, rerun it with the sandbox explicitly disabled.
  A halted session once concluded "toolchain unrecoverable" because all five
  of its recovery attempts were silently sandboxed no-ops.
- **Never kill CoreSimulatorService routinely** (the wrapper once did it every
  iteration and manufactured the wedge). It is a recovery move, not hygiene.
  An orphaned root `simdiskimaged` (`managed_by` → dead pid) does NOT need
  clearing — a fresh CoreSimulatorService pairs with it fine.
- **Toolchain note (Xcode 26.5, since 2026-06-18).** Xcode was upgraded 26.4.1 →
  **26.5** to fix the Xcode 26.4 `simdiskimaged` crash that repeatedly wedged the
  loop under UI-test load (CoreSimulatorService dies under sustained `xcodebuild
  test`; verified fixed on 26.5, even on macOS 26.3.1 — no macOS upgrade needed).
  Two non-obvious consequences:
  - **Do *not* bump the runtime pin to 26.5.** The resolver matches the iOS 26.4
    runtime so tests stay off the iOS-26.5 StoreKit-broken runtime (ADR 0009 /
    the StoreKit trap below). Upgrading the *toolchain* and bumping the
    *runtime pin* are independent — only the toolchain moved.
  - **The iOS 26.5 simulator runtime must stay installed** (Xcode → Settings →
    Components). Xcode 26.5 refuses to enumerate *any* iOS simulator destination
    until its own platform is present; with it installed, 26.2 / 26.4.1 / 26.5 all
    resolve and the 26.4 pin works. It is installed but never the test target.
  - Rollback if ever needed: `Xcode-26.4.1.app` is kept alongside —
    `sudo xcode-select -s /Applications/Xcode-26.4.1.app/Contents/Developer`.

### Why the flags (this is not optional ceremony)

A test that *hangs* (an `await` that never resolves, a network/StoreKit call,
a stuck simulator) otherwise consumes the entire 45-min afk iteration, gets
SIGALRM-killed (`rc=142`), and repeats — burning the loop's whole budget with no
diagnostic. The flags convert that into a legible failure:

- `-test-timeouts-enabled YES` + `-default-test-execution-time-allowance 120`
  fails any individual test that runs longer than 120s, with a stack trace.
- the `scripts/xctimeout` wrapper above bounds everything *outside* a single test
  (xcodegen, simulator boot, linking) so even those fail fast. The `720` cap is
  sized for a **single-suite** local run; do **not** reuse it for the full suite.

**The full suite is not capped by a fixed total time — and deliberately so.**
A fixed wall-clock cap conflates two different concerns: catching a *hang* vs.
bounding a *healthy* suite's runtime. As the app grows deep, sheet-based flows
(localization, language switch, meaning gate…) each gets end-to-end UI coverage,
and the UI suite legitimately grows — every test pays a ~5-9s app-relaunch tax
plus real interaction time. Tie the hang gate to total time and a healthy suite
eventually trips it: that is exactly what wedged PR #203 (every test *passed*;
the suite merely ran past the old 1200s CI cap, and the alarm firing mid-teardown
of a passing test looked like a hang). So `.github/workflows/afk-ci.yml` uses a
**no-progress watchdog** instead: it kills `xcodebuild` only after 300s of *total
silence* in the log (a genuine wedge — healthy runs print `t = N.Ns` polling
lines ~1/s). Concerns cleanly separated: per-test hangs → the 120s allowance;
runner/sim wedge → the watchdog; ultimate backstop → the job's `timeout-minutes`.
If you run the **whole** suite in-session (e.g. the auditor), prefer the same
silence-based signal over a tight `xctimeout` — the full suite will outgrow any
fixed number.

If you find yourself waiting minutes for a test command with **no output**, it is
hanging — kill it and treat it as a failure; do not wait it out. (Steady output
that is merely *slow* is a big suite, not a hang — let it run.)

## Test-output gotchas

- **Phantom "0 tests".** An empty XCTest runner can print `Executed 0 tests`
  while the real result is elsewhere. Trust the `** TEST SUCCEEDED **` /
  `** TEST FAILED **` line and the per-suite count, not a bare "0 tests".
- The `slice-gate` GitHub check is a deliberate no-op (always green). Real
  verification is the in-session test run; do not read meaning into it.

## StoreKit testing — the trap that wedged this loop once

**Do not gate any criterion on driving a real purchase through `SKTestSession`
under `xcodebuild test` from the CLI.** On recent simulator runtimes (notably
iOS 26.5) the CLI does not push the `.storekit` configuration to the simulator's
`storekitd`, so `SKTestSession.buyProduct(...)` either throws
`SKInternalErrorDomain Code=3` or silently falls through to the production App
Store and **hangs indefinitely**. It only works through Xcode's IDE launch path
(Cmd+U), which the public CLI cannot invoke. This is an Apple platform defect,
not something an implementer can code around — it is what burned three 45-min
iterations on the C6 entitlement slice.

**The pattern instead — wrap StoreKit behind an injectable protocol:**

- `EntitlementProvider` depends on a small `EntitlementTransactionSource`
  protocol (`func activeProductIDs() async -> Set<String>`).
- Production conforms via StoreKit 2's `Transaction.currentEntitlements`
  (a thin adapter, correct by inspection).
- **Tests inject an in-memory fake** and feed it product IDs — verifying the
  entitlement *logic* (active/inactive derivation) headlessly, deterministically,
  in milliseconds, with no `storekitd`, no simulator purchase, no network.

The real StoreKit adapter, if you want it exercised end-to-end, gets at most a
**single** `SKTestSession` integration test marked non-blocking (run in the Xcode
IDE / a manual lane), never on the loop's gating path. See ADR 0009 and the C6
criterion in `docs/GOAL.md`.

## Watching the loop

`afk-run.sh`'s `wrapper.log` only shows per-iteration start/done lines — the
slice work runs as an Agent-tool subagent inside each headless session, so its
blow-by-blow is persisted to `~/.claude/projects/<repo-slug>/<uuid>.jsonl` (the
orchestrator) and `<uuid>/subagents/agent-*.jsonl` (the worktree work), not to
`wrapper.log`. `scripts/afk-tail.py` (read-only) follows both and renders them
in the wrapper's `TS |   · …` format, nesting subagent lines as `↳`. Use it via:

```bash
./scripts/afk-watch.sh          # run the loop + follow it live (Ctrl-C stops both)
./scripts/afk-tail.sh           # just follow (loop already running elsewhere)
tail -f .afk/stream.log         # ...or tail the persisted render from anywhere
```

## Screenshot evidence — the `afk-evidence` release must pre-exist

The loop publishes UI screenshots by uploading them as assets on a GitHub
**release tagged `afk-evidence`** (a pre-release) and inline-embedding the
download URL (`…/releases/download/afk-evidence/slice-<N>-<desc>.png`) in the
issue/PR comment. The repo is public, so `![…]` embeds render.

**The trap:** *creating* a release is a sensitive outward-facing action the
harness permission classifier declines autonomously, but *uploading an asset to
an existing release* is allowed. So if `afk-evidence` does not yet exist, the
very first slice's screenshot fails to land — the comment falls back to a text
"⚠️ visual evidence did not land" explanation (this is exactly what happened to
#85; the PNG was recovered post-hoc from the `.xcresult` in DerivedData via
`xcrun xcresulttool export attachments` and uploaded once the release existed).

**Therefore: pre-create the `afk-evidence` release during `afk-init`** (e.g.
`gh release create afk-evidence --prerelease --notes "afk loop screenshot
evidence"`) so the per-slice upload path is never blocked mid-loop. Naming
convention for assets: `slice-<N>-<short-desc>.png`.
